Support desk — make the reply workflow safe and usable

CASE JI-SUPPORT-DESKBACKENDUIDATA MODELSECURITY

Executive summary. The inherited inbox could duplicate inbound messages, let one organization read and change another's tickets, send an edited draft without re-approval, send the same reply several times on overlapping clicks, retry a timed-out delivery with a fresh reference (delivering twice) while recording nothing, and let automation reply after a human took over. All six required behaviours are now enforced on the server with database constraints and compare-and-set transitions, verified by 57 tests (20 of them fail on the original code) and by a black-box before/after battery (baseline 2/13, feature 13/13).

1. What changed, in plain words

  • Inbound: the same event (per organization) is stored once, even if it arrives many times at once or after a restart.
  • Isolation: an agent only ever sees and changes their own organization's tickets; guessing an id returns "not found".
  • Approval: approval belongs to one exact version of the text; any edit removes it; overlapping clicks send once.
  • Delivery: the app writes down the attempt before calling the provider. If the provider's answer is uncertain, the attempt is UNKNOWN and is never resent automatically; "Check delivery" asks the provider by reference.
  • Takeover: once a human owns the conversation, automation cannot send; the human still can.
  • Inbox: shows state, owner, approval, attempts, an audit trail with who did what, and the next safe action.

2. Data seed and setup

No manual seed. Migration v1 creates the starter schema and the two fixture tickets (101 Alpha, 202 Beta); v2–v5 add approval metadata, timestamps, the audit actor, inbound_events, and rebuild attempts with origin/actor and partial unique indexes. An existing starter data/desk.sqlite is upgraded in place (covered by a test).

7. Operator runbook

  1. UNKNOWN: do not resend or edit to resend (the server refuses). Click Check delivery.
  2. Confirmed → SENT; nothing else to do. duplicate_delivery_detected in the audit means the provider holds more than one delivery for the reference: contact the customer.
  3. Still inconclusive → verify with the provider console or the customer; then Mark not delivered with a reason and send again.
  4. FAILED after a 503 → safe to send again.
  5. After a restart, in-flight sends appear as UNKNOWN with recovered_after_restart; follow step 1.

8. Risks and production notes

Single process with SQLite; guarantees rely on constraints that carry over to Postgres. Provider lacks idempotency keys, so an operator's wrong "mark not delivered" can still duplicate (audited, not prevented). Encryption key from DESK_DATA_KEY (dev fallback derived from a fixed passphrase); production needs KMS and rotation. Fixture bearer tokens stand in for authentication. Not production-ready by design; see HANDOFF.md.
